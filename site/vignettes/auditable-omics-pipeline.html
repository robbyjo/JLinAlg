Auditable omics research pipeline

A deterministic study contract, approval-gated execution, amendments, provenance, and guarded future LLM assistance.

Source-build feature. The version-1 study contract, deterministic planner, approval gate, resumable runner, amendments, hash-chained provenance, research notebook, unusual-result observations, and searchable evidence index are implemented. Modality-specific automatic pipelines remain limited to the registered operations described below; unsupported evidence steps stop with a visible request rather than fabricating a result.

Purpose

The pipeline starts from quantified or processed molecular matrices, previously calculated association results, or later-stage evidence. A scientist describes the study and hypotheses; JLinAlg validates the description, constructs a fixed analysis plan, executes the supported operations, and records how every result was produced.

The execution kernel is deterministic and does not require an LLM. Optional bounded assistance defaults to audited manual browser handoff, with explicit OpenAI/Gemini or OpenAI-compatible API alternatives. It can review aggregate findings, suggest analyses, support literature review and draft an unreviewed manuscript. Browser responses are human-attested, not authenticated provider output. A future local adapter may help draft the study description, investigate unusual results, or propose plan amendments. It must use the same validated contracts and cannot bypass JLinAlg's execution, approval, or audit rules.

The intended evidence path follows the central dogma while retaining cohort, tissue, cell, assay, and processing context:

text
genome -> epigenome -> transcription/splicing -> protein -> pathway -> phenotype
   ^                                                               |
   +---- fine mapping, colocalization, MR, prior knowledge ----------+

The objective may be publication, drug-discovery prioritization, or both.

The first study questions and decisions tranche uses built-in rules to document hypothesis-linked questions, collect checked batch answers, propose amendments, and gate affected operations. Questions and answers are preserved in QUESTIONS.md, the session notebook, and the local index. Optional LLM-suggested questions now enter the same review inbox; interactive prompting remains future work. The bioinformatics evidence workflow documents source discovery, reviewed regional genetic inference, protein/sequence investigation, non-LLM literature search and local evidence archives.

Human contract, resolved contract, and executable plan

The project uses three separate documents:

  1. study.yaml is the concise, human-authored scientific contract.
  2. resolved-study.yaml is generated by JLinAlg. It expands every default, records every assumption, resolves paths and identifiers, and is approved and hashed before analysis.
  3. analysis-plan.yaml is the exact operation graph compiled from the resolved contract. It contains no unstated inference about the study.

YAML and JSON represent the same logical object. YAML is the recommended human-facing form; JLinAlg canonicalizes either representation before hashing. The original study file is never silently rewritten.

The Java validator is authoritative. Editor and integration tooling can use the study version-1 JSON Schema and amendment version-1 JSON Schema.

Minimal study schema

Only the project, datasets, and hypotheses are normally required. Cohorts and their relationships are added when they clarify subcohorts, overlap, kinship, or other dependence.

yaml
schema_version: 1

project:
  id: bmi-molecular-study
  title: Multi-cohort molecular analysis of BMI
  description: >
    Discover molecular associations with BMI, validate them, and investigate
    functional and genetic support.
  objective: publication

# Optional. These are the resolved defaults when the block is omitted.
resources:
  downloads: automatic
  directory: resources
  ld:
    database: 1000g-phase3
    population: auto
    auto_download: true

cohorts:
  - id: fhs-offspring
    parent: fhs
  - id: fhs-gen3
    parent: fhs
  - id: fhs-nos
    parent: fhs
  - id: whi

cohort_relationships:
  - between: [fhs-offspring, fhs-gen3]
    type: parent_offspring
  - between: [fhs-offspring, fhs-nos]
    type: spouses

datasets:
  - id: fhs-offspring-expression
    cohort: fhs-offspring
    type: transcriptomics
    tissue: whole_blood
    stage: processed_matrix
    description: Normalized whole-blood transcript abundance.

    files:
      matrix: data/fhs-offspring/expression.tsv
      phenotype: data/fhs-offspring/phenotypes.tsv
      features: data/fhs-offspring/features.tsv

    columns:
      sample_id: sample_id
      feature_id: transcript_id
      phenotypes:
        bmi: BMI
      covariates:
        age: age
        sex: sex
        smoking: smoking_status

  - id: fhs-gen3-expression
    cohort: fhs-gen3
    type: transcriptomics
    tissue: whole_blood
    stage: processed_matrix
    files:
      matrix: data/fhs-gen3/expression.tsv
      phenotype: data/fhs-gen3/phenotypes.tsv
    columns:
      sample_id: sample_id
      feature_id: transcript_id
      phenotypes:
        bmi: BMI
      covariates:
        age: age
        sex: sex
        smoking: smoking_status

  - id: whi-expression
    cohort: whi
    type: transcriptomics
    tissue: whole_blood
    stage: processed_matrix
    files:
      matrix: data/whi/expression.tsv
      phenotype: data/whi/phenotypes.tsv
    columns:
      sample_id: sample_id
      feature_id: transcript_id
      phenotypes:
        bmi: BMI
      covariates:
        age: age
        sex: sex
        smoking: smoking_status

hypotheses:
  - id: H1
    description: Transcript abundance is associated with BMI.
    outcome: bmi
    exposure: all_features
    covariates: [age, sex, smoking]

    inputs:
      discovery:
        - fhs-offspring-expression
      replication:
        - fhs-gen3-expression
        - whi-expression

      goals:
        - association
        - discovery_replication
        - meta_analysis
        - gene_ontology
        - pathway_enrichment
        - genetic_support
        - literature_support

Biological context is carried by each dataset rather than repeated in a separate top-level section. A dataset may add source, anatomical site, compartment, assay, species, visit, cell type, genome build, annotation release, measurement units, or other fields only when they matter.

Discovery, replication, and sensitivity roles belong to the hypothesis because the same cohort may have a different role for another hypothesis. The project objective may be one value or an ordered list, such as publication, drug_discovery_prioritization, or both.

Defaults remain visible

Omitted optional values are expanded in resolved-study.yaml. Version 1 uses these defaults:

Omitted value Resolved default
Project objective publication
Analysis mode auto, deterministic rule planner
Two distinct root cohorts assumed independent
Subcohorts with the same parent potentially dependent; request confirmation
File format infer from extension and verify
Matrix input stage processed_matrix
Results input stage association_results
Direction two-sided
Multiple testing BH at FDR 0.05 over the declared family
Seed derived from the approved plan hash
Audit trail and session history enabled
Existing output reuse only a verified complete artifact

An assumed relationship is an auditable assumption, not a discovered fact:

yaml
assumptions:
  - id: relationship-cohort-a-cohort-b
    statement: cohort-a and cohort-b are independent
    source: default_due_to_undeclared_relationship
    review_status: pending

JLinAlg presents material defaults and assumptions for approval before execution.

Starting from association results

A project need not begin with a matrix. A results table is a dataset at a later processing stage.

yaml
datasets:
  - id: fhs-expression-associations
    cohort: fhs-offspring
    type: transcriptomics
    tissue: whole_blood
    stage: association_results
    description: Previously calculated transcript-BMI associations.

    files:
      results: results/fhs/transcript-bmi.tsv
      features: data/fhs/features.tsv

    columns:
      feature_id: transcript_id
      effect: beta
      standard_error: se
      p_value: p
      sample_size: n

    analysis_description:
      outcome: bmi
      effect_unit: BMI units per normalized-expression unit
      model: linear_regression
      covariates: [age, sex, smoking]

    provenance:
      software: external
      version: unknown
      auditability: partial
      gaps:
        - Original command and normalization parameters were unavailable.

  - id: whi-expression-associations
    cohort: whi
    type: transcriptomics
    tissue: whole_blood
    stage: association_results
    files:
      results: results/whi/transcript-bmi.tsv
    columns:
      feature_id: transcript_id
      effect: beta
      standard_error: se
      p_value: p
      sample_size: n

hypotheses:
  - id: H1
    description: Transcript abundance is associated with BMI.
    inputs:
      discovery: [fhs-expression-associations]
      replication: [whi-expression-associations]
    analysis:
      mode: auto
      goals:
        - discovery_replication
        - meta_analysis
        - gene_ontology
        - pathway_enrichment
        - literature_support

JLinAlg begins at harmonization and replication instead of recalculating the association. Available columns determine eligible downstream operations. Feature IDs and p-values may support enrichment; meta-analysis also requires compatible effects and uncertainty; allele-aware genetic operations require alleles, positions, genome build, and other method-specific fields. An unavailable prerequisite blocks the operation with an explanation rather than a guessed value.

Multi-phenotype result files and strict feature universes

A physical result file may contain several outcomes. Declare one logical dataset per outcome and let those datasets reuse the same files.results path with different column mappings. This keeps each hypothesis and estimand explicit without copying the source data. A blank first CSV header produced by R row names is exposed as the reserved __row_name__ column.

For result sets that must reproduce a predefined eligible-feature universe, add column validity rules and an explicit harmonization policy:

yaml
datasets:
  - id: fhs-bmi
    cohort: fhs
    type: transcriptomics
    stage: association_results
    files: {results: results/splicing-bmi-fhs.csv}
    columns:
      feature_id: __row_name__
      effect: Fx_BMI
      standard_error: SE_BMI
      p_value: P_BMI
      sample_size: N_BMI
      validation:
        finite: [Fx_BMI, SE_BMI, P_BMI, N_BMI]
        positive: [N_BMI]
        nonnegative: [SE_BMI]
        probability: [P_BMI]

hypotheses:
  - id: H-BMI
    description: FHS BMI associations replicate in validation cohorts.
    inputs:
      discovery: [fhs-bmi]
      replication: [cardia-bmi, jhs-bmi, whi-bmi]
    analysis:
      goals: [discovery_replication, meta_analysis]
      harmonization:
        invalid_rows: exclude
        common_universe: intersection
      multiple_testing: {method: BH, alpha: 0.05}
      replication:
        adjustment_scope: discovery_subset
        require_same_sign: false
        threshold_comparison: less_than

common_universe: intersection retains only feature IDs eligible in every input dataset. adjustment_scope: discovery_subset recomputes each validation cohort's multiple-testing adjustment only over discovery-selected features. Direction is still reported, but it affects replication eligibility only when require_same_sign: true. These choices are scientifically consequential and therefore must be declared rather than inferred. Defaults remain conservative: invalid rows are errors, no intersection is imposed, adjustment covers all results, sign agreement is required, and the threshold comparison is inclusive.

LLM-assisted drafting

An LLM may eventually help translate protocols, meeting notes, data dictionaries, or a conversation into a proposed study file. That draft remains a proposal:

text
notes and data inventory
        |
        v
LLM-proposed study.yaml
        |
        v
schema and cross-reference validation
        |
        v
resolved defaults and questions
        |
        v
scientist approval
        |
        v
immutable approved contract

The LLM must not invent unavailable metadata, infer independence from naming, or promote an outcome-informed hypothesis to confirmatory. Missing material facts become questions or explicit unknown values. If a remote LLM is used, project policy controls which information may leave the local environment.

An adopted LLM draft records the provider, reported model identifier or local model hash, prompts, supplied context hashes, response, scientist edits, and approval. The future connection may be local, direct API, OAuth-authorized, or MCP-based without changing the study schema.

JLinAlg may also generate an AGENTS.md working brief from the approved resolved contract. It contains the project scope, active hypotheses, data-access policy, approved commands, output layout, audit requirements, and actions requiring scientist approval. It is a derived, hashed view for an LLM or other agent, not another source of scientific truth; changes return through study or amendment validation.

Diagnostic review and unusual findings

Fixed pipelines cannot enumerate every meaningful visual pattern. JLinAlg emits registered deterministic diagnostics, and study observe records unusual observations without prematurely labeling them as biology or processing error. Examples include off-diagonal streaks in effect comparisons, unexpected clusters, sign discordance, batch-aligned bands, heteroscedastic fans, genomic inflation, and isolated high-leverage groups.

Each observation receives a stable ID and records the plot and source-data hashes, detector and actor, timestamp, affected cohorts and hypotheses, quantitative support, competing explanations, suggested checks, and final disposition. Deterministic checks run first. A future LLM may inspect the plot and its declared context, explain plausible biological and technical causes, and propose discriminating analyses. It cannot silently relabel a result or add an analysis to the approved plan.

If the scientist accepts a proposed direction, such as batch sensitivity, stratification, reprocessing, or independent replication, it becomes an amendment. The original plot, observation, discussion, rejected explanations, decision, and resulting artifacts remain linked in the evidence graph.

Project progress status

The generated file is state/project-status.yaml. If it is absent, the project is at its beginning: no compiled or executed project state is claimed.

yaml
schema_version: 1
project_id: bmi-molecular-study
study_hash: "<64-character SHA-256 hex>"
resolved_study_hash: "<64-character SHA-256 hex>"

state: waiting_for_plan_approval
phase: planning
updated_at: 2026-10-05T14:22:31Z
last_event_id: event-000042

active_plan:
  plan_id: plan-0123456789ab
  plan_hash: "<64-character SHA-256 hex>"
  status: proposed

hypotheses:
  H1:
    status: approved

pending_assumptions: 1

pending_decisions:
  - id: approve-plan-0123456789ab
    type: plan_approval

applied_amendments:
  - meeting-2026-10-01

operations:
  completed: 0
  reused: 0
  waiting: 0

Suggested project states are planning, waiting_for_approval, ready, running, waiting_for_input, completed, failed, and archived. This file is a disposable materialized view of the event ledger, not the ledger itself. JLinAlg regenerates it after every committed event. Users and LLMs may read it but do not edit it to change project state.

Amendment files

Project evolution is recorded in amendment-XXX.yaml, where XXX is a unique, user-chosen identifier safe for a filename. Examples include amendment-meeting-2026-10-01.yaml and amendment-add-whi.yaml.

An amendment names the approved contract on which it is based and contains only the additions, updates, retirements, or new analysis directions. Added and updated objects use the same structure as study.yaml. Copy resolved_study_hash exactly from study status; version 1 emits the raw lower-case 64-character SHA-256 hexadecimal value.

yaml
schema_version: 1

amendment:
  id: meeting-2026-10-01
  title: Add a replication cohort and investigate batch sensitivity
  base_study_hash: "<resolved_study_hash from study status>"
  proposed_at: 2026-10-01T16:30:00Z
  proposed_by:
    type: human
    id: investigator-01
  source:
    type: meeting
    id: analysis-team-2026-10-01
  rationale: >
    WHI data became available, and the discovery QC suggested that the primary
    result should be tested for sensitivity to processing batch.

changes:
  add:
    cohorts:
      - id: whi

    datasets:
      - id: whi-expression
        cohort: whi
        type: transcriptomics
        tissue: whole_blood
        stage: processed_matrix
        files:
          matrix: data/whi/expression.tsv
          phenotype: data/whi/phenotypes.tsv
        columns:
          sample_id: sample_id
          feature_id: transcript_id
          phenotypes:
            bmi: BMI
          covariates:
            age: age
            sex: sex

    analysis_requests:
      - id: SA1
        type: sensitivity_analysis
        for_hypothesis: H1
        description: Refit H1 with processing batch and compare effect changes.
        reason: Discovery QC showed possible batch-associated structure.

  update:
    hypotheses:
      - id: H1
        inputs:
          replication:
            append: [whi-expression]

  retire:
    datasets:
      - id: old-pilot-expression
        reason: Superseded by the complete quantified release.

Retirement never deletes an artifact or historical result. It prevents future plans from treating that object as current and records why it changed.

Amendment lifecycle

  1. A person, JLinAlg, or a future LLM proposes the amendment.
  2. JLinAlg validates identifiers, schema, base hash, scientific dependencies, testing-family effects, and affected downstream artifacts.
  3. JLinAlg shows an impact preview.
  4. The scientist approves, rejects, revises, or defers it.
  5. Approval is recorded in the event ledger and SESSION_HISTORY.md.
  6. JLinAlg produces a new resolved contract and plan; it does not rewrite the base study or prior plan.

Applied order is recorded in the ledger and project-status.yaml. Filename sorting does not determine scientific precedence. A revised proposal uses another unique amendment ID or explicit revision; an approved amendment is immutable.

Hypothesis evolution

Hypotheses retain stable IDs and explicit states such as proposed, approved, active, tested, supported, not_supported, inconclusive, blocked, premise_not_satisfied, retired, and superseded.

An expected dependency may be declared in the initial contract:

yaml
hypotheses:
  - id: H2
    description: Validated transcripts mediate genetically influenced risk.
    depends_on:
      - hypothesis: H1
        criterion:
          minimum_validated_features: 1
        on_failure: premise_not_satisfied

An unexpected objective arising from H1 is added through an amendment and is marked outcome-informed:

yaml
changes:
  add:
    hypotheses:
      - id: H3
        description: Investigate transcript-specific effect-scaling patterns.
        origin:
          classification: outcome_informed_exploratory
          derived_from:
            hypothesis: H1
            result: H1/trans-effect-correlation
        validation_requirement: independent_cohort

A hypothesis generated from inspected results cannot become confirmatory on the same data merely because its result is strong. The report preserves its origin, the evidence visible when it was proposed, and its validation requirement.

Deterministic orchestration first

The implementation uses a rule-based planner and registered operations. Each registry entry declares its executor, accepted stages and modalities, outputs, and diagnostics; the compiled plan pins its datasets, dependencies, and explicit configuration. Richer estimand and resource-limit declarations remain part of the pipeline-profile roadmap.

The planner may start from matrices, association results, or later supported artifacts and constructs only the remaining operations:

text
validate and harmonize
  -> cohort/tissue association when needed
  -> discovery-replication comparison
  -> meta-analysis
  -> feature mapping and enrichment
  -> scoring, fine mapping, colocalization, or MR when eligible
  -> literature and prior-knowledge evidence
  -> publication or prioritization report

analysis.mode defaults to auto. In auto mode, listed goals are a minimum, not a ceiling: JLinAlg adds goals implied by input stages, omics types, cohort roles, and the project objective. Use mode: manual only when the contract should run exactly the listed goals. Functional, genetic, literature, diagnostic, and report branches are independent, so a missing MR input does not suppress enrichment or reporting.

Public reference resolution is inbound-only. With the default resources.downloads: automatic, JLinAlg stores downloaded references in the project resource directory and records source metadata and hashes. The standalone JAR embeds its HTTPS transport, so no external download utility is required. GENCODE releases are inferred from dataset.annotation_release; the versioned transcript-ranking and HGNC metadata tables provide the local feature-to-gene map. GO and Reactome collections are downloaded for local enrichment. LD-dependent configured work defaults to the cataloged, checksum-verified 1000g-phase3 package containing AFR, AMR, EAS, EUR, and SAS panels. That approximately 1.6 GB package is fetched only after eligible variant-level inputs are present. population: auto does not silently substitute a European panel: analysis waits for ancestry when a particular panel is required. Set downloads: manual or deny to prohibit automatic fetches.

The compiled plan is deterministic and resumable without an LLM. A later LLM planner will propose the same typed plan and amendment objects; JLinAlg will continue to own validation, execution, permissions, artifacts, and audit state.

Provenance and the research notebook

Every operation creates overwrite-protected, hashed artifacts and a manifest whose hash is anchored in the event ledger. Events identify the plan, operation, inputs, outputs, configuration, timestamps, status, and responsible actor. Actor types include human, jlinalg, external software, and llm with its reported provider/model or local model hash. study verify checks the base and resolved contracts, plans, amendments, observations and their artifacts, derived notebook files, manifests, and output hashes against that chain.

SESSION_HISTORY.md is required as the readable research notebook. Its machine-readable source is an append-only event ledger. Corrections append a new event; they do not erase the prior record. Relevant discussions remain proposals until an explicit decision commits a study, hypothesis, or plan change.

If an unauditable external tool is used, its output may be imported with a hash, known software information, supplying person, reason for acceptance, and an explicit provenance gap. Downstream results inherit that limitation instead of hiding it.

The current portable layout keeps the same evidence discoverable without special software:

text
project/
  study.yaml
  resolved-study.yaml
  AGENTS.md
  amendments/amendment-XXX.yaml
  state/project-status.yaml
  ledger/events.jsonl
  SESSION_HISTORY.md
  plans/<plan-id>/
  runs/run-<plan-id>/
    run-manifest.yaml
    operations/<operation-id>/{manifest.yaml,artifacts...}
  resources/{gencode,enrichment,ld}/...
  index/{index.json,index.html,evidence-summary.json,LLM_CONTEXT.md}

Generated paths and filenames are recorded in the ledger; moving a portable archive does not break result IDs or internal evidence links.

Traceable reports and submission archives

Current generated reports distinguish complete, waiting, and failed evidence, list stable result IDs and dependency manifests, and create publication and, when requested, drug-discovery evidence inventories. They do not invent narrative or causal conclusions. Any future number or figure inserted into a report must resolve to a source table row or statistic, generating operation, plan, configuration, software, and inputs. LLM-written narrative may cite result IDs but must not become the source of a numerical result.

The project index supports lookup by result ID, hypothesis, operation, state, manifest, artifact path, and SHA-256 hash. index/evidence-summary.json is the portable machine view. index/LLM_CONTEXT.md is a compact retrieval handoff that states hypotheses, evidence states, artifacts, blockers, audit locations, deterministic cross-cohort diagnostics, and a bounded set of leading enrichment or candidate rows. It is still an index: an LLM or human drafter must trace every numerical claim to the referenced artifact and manifest.

Future journal or regulatory archive packaging will include the approved and resolved contracts, plans, amendments, project status, event ledger, SESSION_HISTORY.md, reports, scripts, logs, software inventory, checksums, signatures, and verification instructions. Controlled source data may be represented by hashes and access instructions rather than redistributed.

Current CLI workflow

Build the executable and inspect the study commands:

powershell
.\gradlew.bat executableJar
java -jar build/cli/jlinalg-0.3.6.jar study --help

Create a template or validate an existing YAML/JSON contract. --check-files also verifies every declared file path relative to the study file.

powershell
java -jar build/cli/jlinalg-0.3.6.jar study init --template association-results --out study.yaml
java -jar build/cli/jlinalg-0.3.6.jar study validate study.yaml --check-files
java -jar build/cli/jlinalg-0.3.6.jar study resolve study.yaml --actor-id scientist-1
java -jar build/cli/jlinalg-0.3.6.jar study plan --project . --actor-id scientist-1
java -jar build/cli/jlinalg-0.3.6.jar study status --project .

Review resolved-study.yaml, its pending assumptions, and the generated plan. Approval is a separate human event. If the plan contains default relationship assumptions, accepting them must be explicit.

powershell
java -jar build/cli/jlinalg-0.3.6.jar study approve --project . --approved-by scientist-1 --accept-assumptions
java -jar build/cli/jlinalg-0.3.6.jar study run --project . --actor-id scientist-1
java -jar build/cli/jlinalg-0.3.6.jar study verify --project .

The default end-to-end lifecycle is also available as one idempotent command:

powershell
java -jar build/cli/jlinalg-0.3.6.jar study auto study.yaml --project . --actor-id scientist-1

This validates declared files, resolves the contract, compiles and records the command-line approval, executes every eligible branch, verifies the audit chain, and rebuilds all indexes. Default independent-cohort assumptions are recorded and accepted by this deliberate invocation. Potential dependence, such as two subcohorts under one parent cohort, generates a documented scientist question and gates the affected comparisons while independent work continues. --accept-assumptions does not resolve that question or establish independence; record and approve an evidence-supported relationship amendment instead. Scientific prerequisite gaps produce indexed blockers and do not make study auto fail; execution or integrity failures return status 2.

study run returns 0 for completion, 2 for invalid or failed execution, and 3 when a registered operation is waiting for an external resource or explicit configuration. --allow-partial changes the last case to a successful process exit without changing the recorded waiting_for_input project state. A verified completed run is reused by default with study run or study auto; --resume remains a compatibility alias. Waiting and failed operations retry in a new immutable attempt. --rerun bypasses completed-result reuse without deleting history; --offline disables built-in network requests. The index distinguishes current from historical attempts and reports connection/policy failures separately from absent scientific evidence.

Amendments have a read-only impact preview and require a named human approver:

powershell
java -jar build/cli/jlinalg-0.3.6.jar study amend amendment-add-whi.yaml --project . --check
java -jar build/cli/jlinalg-0.3.6.jar study amend amendment-add-whi.yaml --project . --approved-by scientist-1

An amendment immediately supersedes the active plan. Compile and approve a new plan before further execution. Once a project is resolved, direct edits to the base study cannot replace the contract; use an amendment so the change remains auditable.

Record an unusual artifact with its competing explanations and a proposed direction. An LLM actor must supply its reported model identifier or local model hash; this records attribution but does not give the LLM approval authority.

powershell
java -jar build/cli/jlinalg-0.3.6.jar study observe --project . `
  --id off-diagonal-1 --type off_diagonal_streak --artifact plots/effects.png `
  --hypothesis H1 --description "Off-diagonal effect streak" `
  --explanation "processing batch" --explanation "biological subgroup" `
  --proposed-direction sensitivity_analysis --amendment-id check-batch `
  --actor-type llm --actor-id local-reviewer --model sha256:MODEL_HASH

study operations lists the typed operation registry. Matrix association, result standardization, discovery/replication comparison, fixed-effect or random-effects meta-analysis, local GO and Reactome enrichment, deterministic cross-cohort diagnostics, transparent candidate ordering, and traceable reporting have direct adapters. GENCODE transcript-to-gene mappings and public enrichment databases are resolved automatically when metadata are sufficient. Variant scoring, fine-mapping, colocalization, and MR accept explicit analysis.operations.<goal> command configuration; absent regional summary statistics, alleles, sample sizes, ancestry, or paired exposure/outcome data produce a hashed request.yaml naming the missing inputs. Configured arguments may use @project@, @output@, @upstream@, @ld_database@, and @ld_population@; requires_ld: true triggers reference resolution. Literature support is currently a recorded evidence request; no network service or LLM is contacted automatically.

The generic matrix association adapter is limited to bulk/generic modalities. Single-cell, spatial, microbiome, and multimodal templates describe a valid contract but do not authorize a bulk model; execution waits for a registered modality-specific operation. Likewise, raw or merely quantified matrices require an explicit analysis.association model and preprocessing decision. For discovery/replication, both discovery selection and replication significance use the declared family correction (BH by default, or explicit NONE). By default, adjustment covers every result, significance is compared inclusively with alpha, and sign concordance is required. A study may instead declare analysis.replication.adjustment_scope: discovery_subset, threshold_comparison: less_than, or require_same_sign: false; the comparison output still reports direction. analysis.operations.meta_analysis may set model: fixed|random and min_cohorts.

The complete runnable result-first project is in the GitHub example directory. The hands-on pipeline tutorial walks through the complete run, amendments, observation capture, and the patient-level data boundary enforced for bounded assistance and the remaining high-assurance work.

LLM privacy and patient-data assurance

Feature annotation and diagnostic follow-up are now described in the tutorial's annotation and next-analysis sections. The source build writes an annotation assessment, retains ambiguous or missing locations, shows annotated primary/meta-analysis previews and explicit input requirements in the evidence dashboard, and emits diagnostic-triggered next-steps.yaml proposals. Gene-name resolution is distinct from verified probe coordinates and feature-matched molecular-QTL evidence.

The tutorial now documents the opt-in typed advisor: JLinAlg constructs allowlisted aggregate previews and retains execution and amendment control. Browser handoff prepares a local packet without sending it; the scientist reviews disclosure, submits manually, and imports a hash-matched transcript. OpenAI/Gemini use official APIs, not scraped websites. An explicitly configured OpenAI-compatible endpoint accepts an API key or provider-issued OAuth bearer token. Only explicitly preapproved registered sensitivity analyses execute. All other suggestions remain review requests. Prompts, answers, decisions, UTC timestamps and model identifiers are retained and hashed within each operation.

Without explicit assistance.enabled and purpose permissions, no LLM call is made. The llm actor type alone is attribution, not a network permission. MCP, provider-specific OAuth login/refresh, general pipeline local-model adapters and unrestricted orchestration remain future work. A separate editorial-only loopback adapter is optional, not the default. The application cannot prove what unrelated software, a manual browser interaction or a separately launched agent did. See the browser handoff tutorial for the recorded audit gap, immutable imports and resume commands.

A broader disclosure milestone will extend the current aggregate_results default eligibility policy: bounded result previews may be transmitted, while patient- or sample-level data remain prohibited. Eligibility is determined by registered artifact type, schema, content and lineage—not by a filename or output directory. Association and meta-analysis summaries, enrichment or fine-mapping results, summary diagnostics and redacted figures may qualify; participant matrices, phenotype/covariate rows, identifiers, individual predictions/residuals and per-person scores do not.

Because unpublished research may itself be highly sensitive, the contract offers a project-level deny_all mode in which no project content is sent to a remote LLM. A denial overrides broader defaults or operation-level requests and is recorded in the audit trail. This denial is enforced by the bounded adapter. Additional per-request human approval, small-cell rules and artifact allowlists currently cause a no-transmission waiting state because those stricter controls are not yet implemented. This is not a general PHI detector or a regulatory assurance certification.

For permitted aggregate transmission, JLinAlg should release only locally checked artifacts into a separate disclosure directory; a human-approved, hash-anchored manifest should name the exact bytes, source result IDs, transformations, destination, provider/model, purpose, and policy decision. The connector should have read-only access to that directory and default-deny network access limited to the approved endpoint. The connector's capability boundary is default-deny even though the project policy permits verified aggregate results. A network-disabled local model remains another deployment option.

Application records alone are insufficient for a strong non-egress claim. High-assurance deployments should reconcile disclosure manifests with independent proxy/firewall logs, test with canary identifiers, restrict the connector's filesystem permissions, and retain an SBOM plus security review. Calling output “aggregate” is not automatically adequate de-identification; release rules must follow the applicable legal and institutional determination. The tutorial gives the complete control and verification model and clearly marks it as planned rather than implemented version-1 behavior.
