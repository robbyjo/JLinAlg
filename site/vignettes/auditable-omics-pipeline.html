Auditable omics research pipeline

A minimal study contract, project status, amendments, provenance, and future LLM-assisted planning.

Roadmap design, not a current CLI contract. This page specifies the proposed deterministic pipeline and provenance subsystem. The commands and schemas below are illustrative until their implementation, validation, and release are complete.

Purpose

The planned pipeline starts from quantified or processed molecular matrices, previously calculated association results, or later-stage evidence. A scientist describes the study and hypotheses; JLinAlg validates the description, constructs a fixed analysis plan, executes the supported operations, and records how every result was produced.

The first implementation is deterministic and does not require an LLM. A future local or remote LLM may help draft the study description, investigate unusual results, or propose plan amendments. It must use the same validated contracts and cannot bypass JLinAlg's execution, approval, or audit rules.

The intended evidence path follows the central dogma while retaining cohort, tissue, cell, assay, and processing context:

text
genome -> epigenome -> transcription/splicing -> protein -> pathway -> phenotype
   ^                                                               |
   +---- fine mapping, colocalization, MR, prior knowledge ----------+

The objective may be publication, drug-discovery prioritization, or both.

Human contract, resolved contract, and executable plan

The project uses three separate documents:

  1. study.yaml is the concise, human-authored scientific contract.
  2. resolved-study.yaml is generated by JLinAlg. It expands every default, records every assumption, resolves paths and identifiers, and is approved and hashed before analysis.
  3. analysis-plan.yaml is the exact operation graph compiled from the resolved contract. It contains no unstated inference about the study.

YAML and JSON represent the same logical object. YAML is the recommended human-facing form; JLinAlg canonicalizes either representation before hashing. The original study file is never silently rewritten.

Minimal study schema

Only the project, datasets, and hypotheses are normally required. Cohorts and their relationships are added when they clarify subcohorts, overlap, kinship, or other dependence.

yaml
schema_version: 1

project:
  id: bmi-molecular-study
  title: Multi-cohort molecular analysis of BMI
  description: >
    Discover molecular associations with BMI, validate them, and investigate
    functional and genetic support.
  objective: publication

cohorts:
  - id: fhs-offspring
    parent: fhs
  - id: fhs-gen3
    parent: fhs
  - id: fhs-nos
    parent: fhs
  - id: whi

cohort_relationships:
  - between: [fhs-offspring, fhs-gen3]
    type: parent_offspring
  - between: [fhs-offspring, fhs-nos]
    type: spouses

datasets:
  - id: fhs-offspring-expression
    cohort: fhs-offspring
    type: transcriptomics
    tissue: whole_blood
    stage: processed_matrix
    description: Normalized whole-blood transcript abundance.

    files:
      matrix: data/fhs-offspring/expression.tsv
      phenotype: data/fhs-offspring/phenotypes.tsv
      features: data/fhs-offspring/features.tsv

    columns:
      sample_id: sample_id
      feature_id: transcript_id
      phenotypes:
        bmi: BMI
      covariates:
        age: age
        sex: sex
        smoking: smoking_status

  - id: fhs-gen3-expression
    cohort: fhs-gen3
    type: transcriptomics
    tissue: whole_blood
    stage: processed_matrix
    files:
      matrix: data/fhs-gen3/expression.tsv
      phenotype: data/fhs-gen3/phenotypes.tsv
    columns:
      sample_id: sample_id
      feature_id: transcript_id
      phenotypes:
        bmi: BMI
      covariates:
        age: age
        sex: sex
        smoking: smoking_status

  - id: whi-expression
    cohort: whi
    type: transcriptomics
    tissue: whole_blood
    stage: processed_matrix
    files:
      matrix: data/whi/expression.tsv
      phenotype: data/whi/phenotypes.tsv
    columns:
      sample_id: sample_id
      feature_id: transcript_id
      phenotypes:
        bmi: BMI
      covariates:
        age: age
        sex: sex
        smoking: smoking_status

hypotheses:
  - id: H1
    description: Transcript abundance is associated with BMI.
    outcome: bmi
    exposure: all_features
    covariates: [age, sex, smoking]

    inputs:
      discovery:
        - fhs-offspring-expression
      replication:
        - fhs-gen3-expression
        - whi-expression

    analysis:
      mode: auto
      goals:
        - association
        - discovery_replication
        - meta_analysis
        - gene_ontology
        - pathway_enrichment
        - genetic_support
        - literature_support

Biological context is carried by each dataset rather than repeated in a separate top-level section. A dataset may add source, anatomical site, compartment, assay, species, visit, cell type, genome build, annotation release, measurement units, or other fields only when they matter.

Discovery, replication, and sensitivity roles belong to the hypothesis because the same cohort may have a different role for another hypothesis. The project objective may be one value or an ordered list, such as publication, drug_discovery_prioritization, or both.

Defaults remain visible

Omitted optional values are expanded in resolved-study.yaml. Suggested initial defaults are:

Omitted value Resolved default
Project objective publication
Analysis mode auto, deterministic rule planner
Two distinct root cohorts assumed independent
Subcohorts with the same parent potentially dependent; request confirmation
File format infer from extension and verify
Matrix input stage processed_matrix
Results input stage association_results
Direction two-sided
Multiple testing BH at FDR 0.05 over the declared family
Seed derived from the approved plan hash
Audit trail and session history enabled
Existing output reuse only a verified complete artifact

An assumed relationship is an auditable assumption, not a discovered fact:

yaml
assumptions:
  - id: relationship-cohort-a-cohort-b
    statement: cohort-a and cohort-b are independent
    source: default_due_to_undeclared_relationship
    review_status: pending

JLinAlg presents material defaults and assumptions for approval before execution.

Starting from association results

A project need not begin with a matrix. A results table is a dataset at a later processing stage.

yaml
datasets:
  - id: fhs-expression-associations
    cohort: fhs-offspring
    type: transcriptomics
    tissue: whole_blood
    stage: association_results
    description: Previously calculated transcript-BMI associations.

    files:
      results: results/fhs/transcript-bmi.tsv
      features: data/fhs/features.tsv

    columns:
      feature_id: transcript_id
      effect: beta
      standard_error: se
      p_value: p
      sample_size: n

    analysis_description:
      outcome: bmi
      effect_unit: BMI units per normalized-expression unit
      model: linear_regression
      covariates: [age, sex, smoking]

    provenance:
      software: external
      version: unknown
      auditability: partial
      gaps:
        - Original command and normalization parameters were unavailable.

  - id: whi-expression-associations
    cohort: whi
    type: transcriptomics
    tissue: whole_blood
    stage: association_results
    files:
      results: results/whi/transcript-bmi.tsv
    columns:
      feature_id: transcript_id
      effect: beta
      standard_error: se
      p_value: p
      sample_size: n

hypotheses:
  - id: H1
    description: Transcript abundance is associated with BMI.
    inputs:
      discovery: [fhs-expression-associations]
      replication: [whi-expression-associations]
    analysis:
      mode: auto
      goals:
        - discovery_replication
        - meta_analysis
        - gene_ontology
        - pathway_enrichment
        - literature_support

JLinAlg begins at harmonization and replication instead of recalculating the association. Available columns determine eligible downstream operations. Feature IDs and p-values may support enrichment; meta-analysis also requires compatible effects and uncertainty; allele-aware genetic operations require alleles, positions, genome build, and other method-specific fields. An unavailable prerequisite blocks the operation with an explanation rather than a guessed value.

LLM-assisted drafting

An LLM may eventually help translate protocols, meeting notes, data dictionaries, or a conversation into a proposed study file. That draft remains a proposal:

text
notes and data inventory
        |
        v
LLM-proposed study.yaml
        |
        v
schema and cross-reference validation
        |
        v
resolved defaults and questions
        |
        v
scientist approval
        |
        v
immutable approved contract

The LLM must not invent unavailable metadata, infer independence from naming, or promote an outcome-informed hypothesis to confirmatory. Missing material facts become questions or explicit unknown values. If a remote LLM is used, project policy controls which information may leave the local environment.

An adopted LLM draft records the provider, reported model identifier or local model hash, prompts, supplied context hashes, response, scientist edits, and approval. The future connection may be local, direct API, OAuth-authorized, or MCP-based without changing the study schema.

JLinAlg may also generate an AGENTS.md working brief from the approved resolved contract. It contains the project scope, active hypotheses, data-access policy, approved commands, output layout, audit requirements, and actions requiring scientist approval. It is a derived, hashed view for an LLM or other agent, not another source of scientific truth; changes return through study or amendment validation.

Diagnostic review and unusual findings

Fixed pipelines cannot enumerate every meaningful visual pattern. JLinAlg should therefore emit standard quantitative diagnostics and plots, then record unusual observations without prematurely labeling them as biology or processing error. Examples include off-diagonal streaks in effect comparisons, unexpected clusters, sign discordance, batch-aligned bands, heteroscedastic fans, genomic inflation, and isolated high-leverage groups.

Each observation receives a stable ID and records the plot and source-data hashes, detector and actor, timestamp, affected cohorts and hypotheses, quantitative support, competing explanations, suggested checks, and final disposition. Deterministic checks run first. A future LLM may inspect the plot and its declared context, explain plausible biological and technical causes, and propose discriminating analyses. It cannot silently relabel a result or add an analysis to the approved plan.

If the scientist accepts a proposed direction, such as batch sensitivity, stratification, reprocessing, or independent replication, it becomes an amendment. The original plot, observation, discussion, rejected explanations, decision, and resulting artifacts remain linked in the evidence graph.

Project progress status

The proposed generated file is project-status.yaml. If it is absent, the project is at its beginning: no compiled or executed project state is claimed.

yaml
schema_version: 1
project_id: bmi-molecular-study
study_hash: sha256:...
resolved_study_hash: sha256:...

state: waiting_for_plan_approval
phase: planning
updated_at: 2026-10-05T14:22:31Z
last_event_id: event-000042

active_plan:
  id: plan-0003
  hash: sha256:...
  status: proposed

hypotheses:
  H1:
    status: approved
    completed_operations: 0
    planned_operations: 7

pending_decisions:
  - id: decision-0007
    type: plan_approval

applied_amendments:
  - meeting-2026-10-01

provenance:
  complete_artifacts: 4
  partial_artifacts: 1
  provenance_gaps: 1

Suggested project states are planning, waiting_for_approval, ready, running, waiting_for_input, completed, failed, and archived. This file is a disposable materialized view of the event ledger, not the ledger itself. JLinAlg regenerates it after every committed event. Users and LLMs may read it but do not edit it to change project state.

Amendment files

Project evolution is recorded in amendment-XXX.yaml, where XXX is a unique, user-chosen identifier safe for a filename. Examples include amendment-meeting-2026-10-01.yaml and amendment-add-whi.yaml.

An amendment names the approved contract on which it is based and contains only the additions, updates, retirements, or new analysis directions. Added and updated objects use the same structure as study.yaml.

yaml
schema_version: 1

amendment:
  id: meeting-2026-10-01
  title: Add a replication cohort and investigate batch sensitivity
  base_study_hash: sha256:...
  proposed_at: 2026-10-01T16:30:00Z
  proposed_by:
    type: human
    id: investigator-01
  source:
    type: meeting
    id: analysis-team-2026-10-01
  rationale: >
    WHI data became available, and the discovery QC suggested that the primary
    result should be tested for sensitivity to processing batch.

changes:
  add:
    cohorts:
      - id: whi

    datasets:
      - id: whi-expression
        cohort: whi
        type: transcriptomics
        tissue: whole_blood
        stage: processed_matrix
        files:
          matrix: data/whi/expression.tsv
          phenotype: data/whi/phenotypes.tsv
        columns:
          sample_id: sample_id
          feature_id: transcript_id
          phenotypes:
            bmi: BMI
          covariates:
            age: age
            sex: sex

    analysis_requests:
      - id: SA1
        type: sensitivity_analysis
        for_hypothesis: H1
        description: Refit H1 with processing batch and compare effect changes.
        reason: Discovery QC showed possible batch-associated structure.

  update:
    hypotheses:
      - id: H1
        inputs:
          replication:
            append: [whi-expression]

  retire:
    datasets:
      - id: old-pilot-expression
        reason: Superseded by the complete quantified release.

Retirement never deletes an artifact or historical result. It prevents future plans from treating that object as current and records why it changed.

Amendment lifecycle

  1. A person, JLinAlg, or a future LLM proposes the amendment.
  2. JLinAlg validates identifiers, schema, base hash, scientific dependencies, testing-family effects, and affected downstream artifacts.
  3. JLinAlg shows an impact preview.
  4. The scientist approves, rejects, revises, or defers it.
  5. Approval is recorded in the event ledger and SESSION_HISTORY.md.
  6. JLinAlg produces a new resolved contract and plan; it does not rewrite the base study or prior plan.

Applied order is recorded in the ledger and project-status.yaml. Filename sorting does not determine scientific precedence. A revised proposal uses another unique amendment ID or explicit revision; an approved amendment is immutable.

Hypothesis evolution

Hypotheses retain stable IDs and explicit states such as proposed, approved, active, tested, supported, not_supported, inconclusive, blocked, premise_not_satisfied, retired, and superseded.

An expected dependency may be declared in the initial contract:

yaml
hypotheses:
  - id: H2
    description: Validated transcripts mediate genetically influenced risk.
    depends_on:
      - hypothesis: H1
        criterion:
          minimum_validated_features: 1
        on_failure: premise_not_satisfied

An unexpected objective arising from H1 is added through an amendment and is marked outcome-informed:

yaml
changes:
  add:
    hypotheses:
      - id: H3
        description: Investigate transcript-specific effect-scaling patterns.
        origin:
          classification: outcome_informed_exploratory
          derived_from:
            hypothesis: H1
            result: H1/trans-effect-correlation
        validation_requirement: independent_cohort

A hypothesis generated from inspected results cannot become confirmatory on the same data merely because its result is strong. The report preserves its origin, the evidence visible when it was proposed, and its validation requirement.

Deterministic orchestration first

The first implementation uses a rule-based planner and registered operations. Every operation declares its inputs, outputs, supported designs, assumptions, estimand, diagnostics, resource bounds, and downstream compatibility.

The planner may start from matrices, association results, or later supported artifacts and constructs only the remaining operations:

text
validate and harmonize
  -> cohort/tissue association when needed
  -> discovery-replication comparison
  -> meta-analysis
  -> feature mapping and enrichment
  -> scoring, fine mapping, colocalization, or MR when eligible
  -> literature and prior-knowledge evidence
  -> publication or prioritization report

The compiled plan is deterministic and resumable without an LLM. A later LLM planner will propose the same typed plan and amendment objects; JLinAlg will continue to own validation, execution, permissions, artifacts, and audit state.

Provenance and the research notebook

Every completed operation creates immutable, hashed artifacts and an event identifying its inputs, outputs, code, configuration, environment, timestamps, status, and responsible actor. Actor types include human, jlinalg, external software, and llm with its reported provider/model or local model hash.

SESSION_HISTORY.md is required as the readable research notebook. Its machine-readable source is an append-only event ledger. Corrections append a new event; they do not erase the prior record. Relevant discussions remain proposals until an explicit decision commits a study, hypothesis, or plan change.

If an unauditable external tool is used, its output may be imported with a hash, known software information, supplying person, reason for acceptance, and an explicit provenance gap. Downstream results inherit that limitation instead of hiding it.

A conventional layout keeps the same evidence discoverable without special software:

text
project/
  study.yaml
  resolved-study.yaml
  AGENTS.md
  amendments/amendment-XXX.yaml
  state/project-status.yaml
  ledger/events.jsonl
  SESSION_HISTORY.md
  plans/<plan-id>/
  runs/<run-id>/{inputs,outputs,logs,diagnostics,provenance}/
  reports/
  index/{index.json,index.html}
  archives/

Generated paths and filenames are recorded in the ledger; moving a portable archive does not break result IDs or internal evidence links.

Traceable reports and submission archives

Every number and figure in a generated report references a stable result ID that resolves to the source table, row or statistic, generating operation, plan, configuration, software, and inputs. LLM-written narrative may cite result IDs but must not become the source of a numerical result.

The searchable project index supports lookup by hypothesis, cohort, tissue, feature, variant, operation, actor, software or LLM, timestamp, status, report, and provenance gap. A portable HTML index accompanies the machine-readable index.

Journal or regulatory archives include the approved and resolved contracts, plans, amendments, project status, event ledger, SESSION_HISTORY.md, reports, scripts, logs, software inventory, checksums, signatures, and verification instructions. Controlled source data may be represented by hashes and access instructions rather than redistributed.

Planned interface

These commands describe the intended workflow and are not implemented yet:

text
jlinalg study validate study.yaml
jlinalg study resolve study.yaml
jlinalg study plan resolved-study.yaml
jlinalg study status
jlinalg study amend amendment-meeting-2026-10-01.yaml
jlinalg audit verify
jlinalg archive build --profile journal
jlinalg archive verify submission.zip

The adoption target is a short study file, focused questions only when an omitted detail changes the science, and complete provenance generated automatically.
